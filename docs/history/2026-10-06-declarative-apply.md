# 2026-10-06 宣言型への移行（1.0.0）

## 困っていたこと

### インタフェイスと状態管理

- 課題が出るたびに AI にコマンドやオプションを足させてきた結果、インタフェイスがバラバラになっていた。引数の解釈がコマンドごとに違い、`add` と `edit` の処理は重複していた。
- 正本が `~/.config/ccron/tasks/*.json` にあった。そのため、プロジェクトのリポジトリを見ても何が定期実行されているか分からなかった。
  - プロジェクト側に置いたプロンプトのファイルが、実際に登録した内容と食い違ったまま放置されていた。
  - デバッグ用に手で作った `com.ccron.*` が launchd に残っていても、`ccron list` には出なかった。

### テストの外にあったバグ

テストが純粋関数（スケジュールのパースと生成）にしか無く、バグは状態遷移と入力の端に溜まっていた。

- `edit --prompt ""` で `PROMPT: unbound variable` になるスクリプトが生成された。
- 不正なスケジュールはスタックトレースのまま落ちた。
- cwd がクォートされておらず、スペースを含むパスで壊れた。
- 生成スクリプトは `cd` の失敗を無視し、launchd の `/tmp` のまま claude を実行していた。
- Bun の `$` は終了コードが 0 以外だと例外を投げるのに、launchctl の終了コードを自分で見るつもりで書かれていた。そのため「載っていないジョブの bootout はエラーにしない」分岐が一度も効いていなかった。

### 実際の使い方

実際に使っているのは、どれも同じ形のジョブ数件だけだった。cwd はプロジェクトのリポジトリ、MCP 設定あり、プロンプトは「スキルを実行して」の一行。やりたいことは、何が動いているかが分かる・足す/直す/消す・動いたか見る・手動で一度流す、の 4 つだけだった。

## 決めたこと

**プロジェクトに置いた宣言ファイル（`ccron.json`）を正本にし、`ccron apply` で launchd をそれに合わせる。**

```json
{
  "jobs": {
    "member-watch": {
      "schedule": "0 17 * * 1-5",
      "prompt": "member-watch スキルを実行して",
      "cwd": "..",
      "mcpConfig": "mcp/slack.json"
    }
  }
}
```

コマンドは 3 つだけにした。

| コマンド                               | 役割                                                                   |
| -------------------------------------- | ---------------------------------------------------------------------- |
| `ccron apply <ccron.json> [--dry-run]` | 宣言と現状の差分を表示し、作成・更新・引き取り・削除を行う             |
| `ccron status <ccron.json>`            | 各ジョブの同期状態・launchd の状態・ログのパス、他のジョブとその所有者 |
| `ccron run <name>`                     | 手動で一度流してログを tail する                                       |

### 設計の原則

1. **状態を二重に持たない。** `~/.config/ccron/` は廃止した。現状は plist・スクリプト・launchctl そのものから読み、差分は「宣言から生成したファイル」と「ディスク上のファイル」の文字列比較で判定する。
2. **`apply` は冪等で、途中で失敗しても再実行で収束する。** ロールバックはしない。宣言が正本なので、原因を直してもう一度 `apply` すればよい。ファイルが一致していても launchd に載っていないジョブは update として扱う。途中で失敗したジョブも次の `apply` で拾われる。
3. **検証は全部先に済ませ、1 つでもエラーがあれば何も書かない。** エラーは短絡させず全部集めて表示する。manifest の知らないキーもエラーにする。typo したキーが黙って無視され、設定したつもりで効いていない、という事故を防ぐため。
4. **複数の manifest が共存できる（所有者）。** 各ジョブの plist に `CCRON_MANIFEST=<manifest の realpath>` を記録する。`apply` が消すのは自分の manifest が作ったジョブだけ。同名のジョブを別の manifest が持っていたら衝突エラーにして何もしない。記録の無いジョブ（手作業や 0.3 以前の ccron が作ったもの）は、同名で宣言すれば引き取る（adopt）。それ以外は触らず、`status` に削除コマンドを表示するだけにする。
   - 比較は realpath で行う。symlink 経由で置かれた manifest を別の所有者と誤判定しないため。
5. **検証したことを型に残す（Domain Modeling Made Functional）。** `JobName`・`NonEmptyString`・`AbsoluteDir`・`ManifestId` などは、検証を通らないと作れない型にした。`Plan` は `plan()` からしか作れず、`execute()` は `Plan` しか受け取らない。現状は直和型（所有者 4 種、ファイルが揃っているか）で表し、`plan` の分岐とテストの表を 1 対 1 で対応させた。
6. **I/O を両端に寄せる。** 読む（I/O）→ parse → plan → render（純粋）→ execute（I/O）の流れにした。`apply` と `status` は同じ `prepare()` を通るので、`status` と `apply --dry-run` の判定は食い違わない。マシンに触るもの（home、生成先のパス、launchctl、claude の場所）は全部引数で渡し、テストでは一時ディレクトリと偽の launchd に差し替える。
7. **プロンプトは一行に留め、中身はプロジェクトのスキルに置く。** ccron は強制しない。運用ルールとする。

## 捨てたもの

| 捨てたもの                                            | 理由                                                                                                             |
| ----------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------- |
| `add` / `edit` / `remove`                             | 宣言ファイルと `apply` で置き換わる                                                                              |
| `list` / `show`                                       | `status` と宣言ファイルを読めば分かる                                                                            |
| `log`                                                 | `tail` するだけ。ログのパスは `status` に出す                                                                    |
| `test`                                                | 静的なチェック（cwd・MCP 設定の存在、TCC）は `apply` の検証に移した。動くかどうかは `run` で実際に流して確かめる |
| `auth`                                                | `claude --mcp-config <path>` を対話で起動するだけの一行ラッパーだった                                            |
| `config.json`（`extraPaths`・`ulimit`・`claudePath`） | 前の 2 つは既定値のまま使われていなかった。claude の場所は `apply` のたびに `which claude` で解決する            |
| cwd 省略時の `/tmp`                                   | 使っておらず、指定し忘れると権限エラーで落ちるだけだった。cwd は必須にした                                       |
| `remove` がログも消す挙動                             | 2026-04-03 の判断を戻した。削除してもログは残す。消したジョブが最後に何をしたか見られるように                    |

`test` の MCP 認証チェックと `auth` は、OAuth の期限切れが頻発するなら残す価値がある。今のところ困った記録が無いので削った。困ったら戻す。

## 残した課題

- manifest を別の場所へ移すと、旧パスのジョブは孤児になり、移動後の `apply` で同名の衝突になる。今は `status` に出る削除コマンドで手で消す。頻繁に起きるなら引き取りの仕組み（`--adopt` など）を考える。
- 一度も実行されていないジョブも `launchctl list` では `LastExitStatus = 0` になるので、`status` に「last exit 0」と出る。
